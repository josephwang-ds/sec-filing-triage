## 建议执行顺序

1. 用 fake clock、来源 fixtures、临时文件和可注入 store 测策略、失败与恢复；不得拿生产数据做删除/损坏演练。
2. 针对真实 bundle 执行 Node API 测试与现有 Python 相关测试；继承无 node 时明确 skip 的项目惯例。
3. 在可用的 staging 持久存储/触发器完成冷启动、重复投递和主调度中断演练；mocked 通过不得代替这一步。
4. 渲染 AAPL/JPM/NVDA（至少包含可用、空数据、过期/失败三个状态）并检查桌面/390px、中英文、键盘。
5. 修改稳定后按仓库配置运行 lint、全量测试和 CI。测试数量用真实 collection 更新，不能复制旧 776 数字。
6. 最多用必要次数进行真实模型请求验收；不存在 API key 时报告配置缺项，不能读取/粘贴 key。
7. 交付 draft PR；Codex 核对功能/来源/部署差异后协调上线。上线后记录连续 48 小时运行结果，再确认运行可靠性验收。

## Release 状态必须分开

- code_ready：实现和对应本地/CI 检查通过。
- staging_verified：真实数据、持久存储、接口、冷启动和故障恢复演练通过。
- production_enabled：生产触发器和数据路径真正启用，用户域名显示新内容。
- reliability_verified：至少 48 小时实际观测与独立恢复演练完成；记录实际延迟分布、缺口和预算。

任何一项未完成都应准确标注。不要把“已写 cron”“HTTP 200”“部署成功”“引用格式校验通过”分别等同于调度可靠、数据新鲜、功能闭环、事实全部正确。
